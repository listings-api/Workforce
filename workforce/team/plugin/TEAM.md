# WorkForce team rules

You work with Codex (an OpenAI agent, via the `mcp__plugin_workforce_codex__*` tools) as one team.

1. For any non-trivial task, first call `mcp__plugin_workforce_codex__codex_plan`: Codex researches and plans. Debate disagreements briefly with `mcp__plugin_workforce_codex__codex_ask`. Still disagreeing after 2 rounds: ask the user (AskUserQuestion) with both positions.
2. You write the code. Delegate small, mechanical, well-specified sub-tasks to the `fast-coder` sub-agent; keep hard or cross-cutting work yourself.
3. Before any commit, get both reviews in one step: `mcp__plugin_workforce_codex__claude_review` and `mcp__plugin_workforce_codex__codex_review`, against HEAD (no custom `base`). The server records each verdict; the approvals files and key are off limits. Fix every REQUEST_CHANGES and re-review; any edit voids both approvals. After 3 rejections in a row the review tools stop: don't commit; show the user both positions verbatim and ask. Only the user's /wf-review-again allows more rounds. `git commit` (also `merge`, `cherry-pick`, `revert`, `am`) is blocked until both approve the exact tree being committed: commit in a command of its own, with nothing before it that changes files (`git add -A && git commit …` is fine), and no explicit paths. Merging existing commits with nothing staged (`git merge origin/master`, `git pull`) needs no review; a conflict resolution does. Pointing a branch at a commit not on it or a remote (`git reset <commit>`, `branch -f`, `checkout -B`) needs both approvals of that commit's files. `rebase`, `git stash` and `update-ref` are refused.
4. Follow the user's git instructions exactly (branch names, pulling, where to commit). Never force-push, never bypass signing, and don't push unless asked.
5. The user picks models. Don't change the Codex model or effort unless the user asks (`/codex-model`, `/codex-effort`).
6. Never paraphrase what Codex or the user said to Codex. When you present Codex's plan, answer or verdict, quote it verbatim (or point to the saved file named in the tool result), then give your own view separately under a label such as "Claude's view". Where the user talked to Codex directly with `@codex`, that exchange appears in your context under "Direct user↔Codex exchange": treat it as the original and quote it, never a summary.
7. Codex is read-only by default. In write mode (`/codex-mode write`) `mcp__plugin_workforce_codex__codex_ask` may edit files, but only ask it to when the user asks for that. Reviews are still required before a commit.
8. In a repo that is a subfolder of the project folder (a folder holding several repos), pass `repo` (its path) to `mcp__plugin_workforce_codex__codex_plan`, `mcp__plugin_workforce_codex__codex_review`, `mcp__plugin_workforce_codex__claude_review` and `mcp__plugin_workforce_codex__review_status`. Approvals are per repo.
